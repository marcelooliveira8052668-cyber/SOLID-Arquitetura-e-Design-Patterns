🚀 Guia de Estudos: SOLID & Design Patterns

Preparação para os exercícios da próxima semana

📖 Revisão Rápida

SOLID: Princípios para criar códigos flexíveis[cite: 1, 2].

  • S: Uma classe/componente deve ter apenas uma razão para mudar[cite: 1].
  • O: Aberto para extensão, fechado para modificação[cite: 1, 2].
  • L: Subtipos devem ser substituíveis sem quebrar contratos[cite: 1].
  • I: Interfaces segregadas (não force dependências inúteis)[cite: 2].
  • D: Alto nível não deve depender de baixo nível; dependa de abstrações[cite: 2].

🧠 Exercícios Práticos com Gabarito

1. O que acontece quando um componente React assume a responsabilidade de buscar dados na API, gerir estados complexos e renderizar a interface ao mesmo tempo[cite: 1]?
Gabarito: Ele viola o Princípio da Responsabilidade Única (S do SOLID)[cite: 1]. Se a API mudar ou o design mudar, o componente é afetado. A solução é separar a lógica de dados (serviços) da apresentação visual[cite: 1].
2. Como o padrão *Strategy* ajuda a evitar estruturas gigantescas de `if/else` no código[cite: 1]?
Gabarito: O padrão *Strategy* isola cada comportamento ou regra de negócio num objeto ou função separada. Em vez de ramificar com vários `if/else`, o código principal mapeia dinamicamente qual estratégia executar, respeitando o princípio Aberto/Fechado[cite: 1].
3. Qual é a principal diferença entre módulos de **Alto Nível** e **Baixo Nível** numa aplicação[cite: 2]?
Gabarito: O Alto Nível lida com as regras de negócio e a interface do utilizador (o "quê" o sistema faz). O Baixo Nível lida com os detalhes técnicos de infraestrutura, como conexões diretas a bases de dados ou bibliotecas de pedidos HTTP (o "como" o sistema faz)[cite: 2].
4. O que diz o Princípio da Inversão de Dependência (D do SOLID)[cite: 2]?
Gabarito: Módulos de alto nível não devem depender diretamente de módulos de baixo nível; ambos devem depender de abstrações[cite: 2]. Isto reduz o acoplamento e facilita a substituição de tecnologias sem quebrar o código principal[cite: 2].
5. O que significa o princípio da Substituição de Liskov (L do SOLID) aplicado a componentes React[cite: 1]?
Gabarito: Significa que um componente especializado (como um botão com ícone) deve poder substituir o seu componente base sem quebrar o contrato esperado pelas propriedades (`props`), garantindo um comportamento previsível[cite: 1].
